## 1. What the backend is for

The GlobeTrot site is a static marketing site. Its one interactive promise is "plan a trip": a visitor describes (or fills in) a trip, and a concierge returns a day-by-day itinerary that follows the live forecast and is checked against the budget.

Backend responsibilities:
1. **Concierge**: LLM conversation with tools (weather, budget, currency) → text plan → validated JSON itinerary.
2. **Content**: `journeys.json` is the source of truth for the Journeys pages; `build.py` generates HTML from it.
3. **Delivery**: serve the site, and connect the site's "Plan a trip" links to the concierge.

Out of scope (from `requirements.md` §4): RAG, accounts/login, payments, bookings, live prices, maps. Revisit only if the user changes scope, then log it in §11.

## 4. Architecture

```
Visitor ──> super-travel (static, :5173) ──"Plan a trip"──> Streamlit concierge (:8501)
                                                              │ chat.py / plan_form.py
                                                              ▼
                                                  llm.new_session()  ── provider() ──┐
                                                              │                      │
                                         Gemini ChatSession ◄─┴─► OpenRouter ChatSession
                                                              │
                              Call 1: tool loop (≤ MAX_TOOL_ROUNDS) ──> tools.run_tool
                                                              │            ├ get_weather  → Open-Meteo
                                                              │            ├ check_budget → pure Python
                                                              │            └ convert_currency → Frankfurter
                              Call 2: draft → JSON → Itinerary (retry once) → _reconcile
                                                              ▼
                                         TurnResult(text, itinerary, tool_calls) → render.py / export.py
```

Hard rules that hold the design together:
- **Two model calls per turn**, on purpose. Tools and strict JSON in one call are unreliable across models.
- **Tools never raise.** They return a dict; failure is `{"error": "<sentence the model can read>"}`.
- **Python does the arithmetic.** `_reconcile` recomputes `estimated_total` and `budget_status`; never trust the model's sums.
- **Errors shown to users are `ChatError` messages**, never stack traces. Everything else is mapped by `friendly_error`.
- **A failed turn leaves history unchanged** (`del self.contents[start:]`).
- **Secrets only in `.env`**, never committed, never printed.

### Option B: HTTP API (built 2026-10-05, `api.py`)
The site is static and cannot talk to Streamlit, so `api.py` is a thin HTTP layer **in front of the same `llm`/`tools` code** (no logic forked). Run: `uvicorn api:app --port 8000` or the `api` entry in `.claude/launch.json`.

| Route | Purpose | Body → Response |
|---|---|---|
| `GET /api/health` | liveness, provider, key present (never the key) | → `{ok, provider, model, has_key}`; bad `LLM_PROVIDER` → `{ok:false, error}` |
| `GET /api/journeys` | content for the site | → `journeys.json` shape |
| `POST /api/chat` | one concierge turn | `{session_id?, message}` → `{session_id, text, itinerary or null, events[{kind,text}], error or null}` |
| `POST /api/chat/reset` | drop a session | `{session_id}` → `{ok}` |
| `POST /api/contact` | contact form | `{name, email, message}` → `{ok}`; appended as one JSON line to `CONTACT_FILE` |

Behaviour that clients rely on:
- **Status codes:** a `ChatError` (no key, rate-limited model, bad key…) is HTTP 200 with `error` set, so one code path shows it; 422 for bad bodies (empty or over 2000 chars, bad email); 429 + `Retry-After` when rate-limited; 500 only if a contact message cannot be saved.
- **Sessions:** ids are issued by the server; an unknown, expired or missing id starts a fresh session and returns its new id (history is lost, so clients must always store the id from the latest response). Idle TTL 30 min, at most 200 sessions (least recently used dropped), one turn at a time per session. In memory only: a restart drops them all.
- **Rate limit:** per client IP, chat 10/min, contact 5 per 10 min. Behind a reverse proxy the IP is the proxy's; add forwarded-header handling before deploying that way.
- **CORS:** only the origin of `SITE_URL`. No auth: the API spends your model quota, so do not expose it publicly without a stronger guard.
Streamlit stays the default UI; both call `llm.new_session()`.

## 5. Module map: what each file owns

| File | Owns | Must not |
|---|---|---|
| `tools.py` | External data + pure logic; the `TOOL_FUNCTIONS` registry; caching | Import `llm`, call a model, raise to the caller |
| `llm.py` | Provider choice, tool *declarations* (`TOOLS`), Gemini loop, error mapping, shared types | Contain business rules that belong in a tool |
| `openrouter.py` | OpenRouter wire format only; reuses `llm.TOOLS`-equivalent, prompts, schema, `ChatError` | Duplicate prompts or tool logic |
| `schemas.py` | The shape of an itinerary | Hold behaviour |
| `prompts.py` | All model-facing text | Embed dates/secrets other than via parameters |
| `render.py` / `export.py` | Presentation of an `Itinerary` | Call tools or models |
| `chat.py` / `plan_form.py` / `app.py` | Streamlit UI and session state | Contain planning logic |
| `super-travel/build.py` | Validate `journeys.json`, generate pages, cache-bust hash | Be bypassed by hand-editing generated HTML |

## 6. Contracts

### 6.1 Tools (model-callable)
Declared in `llm.TOOLS` **and** registered in `tools.TOOL_FUNCTIONS`; described to the user in `llm._describe_call/_describe_result` (OpenRouter reuses all three, converting `TOOLS` to JSON Schema). Change them together.

| Tool | Args | Success result | Error cases (all return `{"error"}`) |
|---|---|---|---|
| `get_weather` | `city, start_date (YYYY-MM-DD), days, country_code?` | `{place, forecast:[{date, temp_max_c, temp_min_c, rain_chance_pct, conditions}], note?}` | no city, bad date, start in past, start beyond 16-day window, city not found, service unreachable, bad format |
| `check_budget` | `activities:[{name, estimated_cost}], budget` | `{total, budget, remaining, status: within\|over}` | unreadable budget, activity without cost |
| `convert_currency` | `amount, from_currency, to_currency` | `{amount, from, to, rate, rate_date?, converted}` | bad amount, bad codes, unsupported pair, service unreachable |

### 6.2 Itinerary schema (`schemas.py`)
`Itinerary{destination, total_days, currency, budget, days[Day], estimated_total, budget_status: within|over}`
`Day{day_number, date, weather_summary, activities[Activity]}` · `Activity{name, time_of_day: morning|afternoon|evening, indoor, estimated_cost}`
`budget` was added to the original spec so the banner can show the limit.

### 6.3 Turn result and events
- `session.send(text, on_event) -> TurnResult{text, itinerary|None, tool_calls[ToolCall{name,args,result}]}`
- `on_event(kind, message)`, kind ∈ `tool | result | retry | format`; the UI shows these as the status line.
- Over HTTP the same events arrive in `events[]` after the turn finishes (no streaming yet).
- An itinerary is produced only when `check_budget` succeeded in that turn. Plain Q&A turns return text only.

### 6.4 Content store (`super-travel/journeys.json`)
Top level `{currency, journeys[]}`. Each journey: `slug, title, category, days, budget, tags[], image (Unsplash id), alt, season, stay, lede, overview[], notes[{label,text}], budget_breakdown, itinerary`.
`build.py` rejects: breakdown that does not sum to budget, day count ≠ itinerary length, unknown setting (Outdoor/Indoor/Mixed). After editing the JSON, `styles.css` or `main.js`, run `python super-travel/build.py`; `test_site.py` fails if generated pages are stale.

## 7. Configuration (`.env`, see `.env.example`)

| Var | Meaning | Default / note |
|---|---|---|
| `LLM_PROVIDER` | `openrouter` or `gemini` | If unset: OpenRouter when only its key exists, else Gemini; invalid value → `ChatError` |
| `OPENROUTER_API_KEY`, `OPENROUTER_MODEL` | OpenRouter | model must support tool calling; default `openai/gpt-4o-mini` |
| `GEMINI_API_KEY`, `GEMINI_MODEL` | Gemini | default `gemini-3.5-flash`; names change, check docs |
| `SITE_URL` | Where the site runs (chat header links; the API's CORS origin) | `http://localhost:5173` |
| `CONTACT_FILE` | Where `/api/contact` appends messages | `data/contact_messages.jsonl` |
| `LOG_LEVEL` | Python log level for the app and API | `INFO` |

Tunables in code: `MAX_TOOL_ROUNDS=5`, `FORMAT_ATTEMPTS=2`, `RETRY_DELAYS_S=(2,6)`, `RETRYABLE_CODES=(429,503)`, `MAX_SERVER_WAIT_S=10` (llm.py); `TIMEOUT_S=10`, `CACHE_TTL_S=1200`, `FORECAST_WINDOW_DAYS=16` (tools.py); `REQUEST_TIMEOUT_S=60` (longest silence) and `REQUEST_DEADLINE_S=90` (hard total per request) (openrouter.py); `CHAT_LIMIT=10/60s`, `CONTACT_LIMIT=5/600s`, `SESSION_TTL_S=1800`, `MAX_SESSIONS=200`, `MAX_MESSAGE_CHARS=2000` (api.py).
External services, no key needed: Open-Meteo geocoding + forecast, Frankfurter (ECB rates).

## 10. Recipes for common changes

**Add a tool** (e.g. `get_attractions`)
1. `tools.py`: function returns a dict, never raises, errors as `{"error": ...}`; add to `TOOL_FUNCTIONS`; cache if it hits the network.
2. `llm.py`: add a `FunctionDeclaration` to `TOOLS`; add cases to `_describe_call` and `_describe_result`.
3. `openrouter.py` converts `llm.TOOLS` to JSON Schema automatically; just confirm the new declaration converts (nested arrays/objects).
4. `prompts.py`: tell the model when to call it and what to do on error.
5. Tests in `test_chatbot.py` (success, each error case, bad args) and a loop test with the fake client.
6. Update §6.1, §5 if a file changed, §9, §12.

**Change the itinerary shape** (e.g. add `transport` to Activity)
`schemas.py` → `prompts.FORMAT_PROMPT` → `_reconcile` if totals are affected → `render.py` and `export.py` → tests → §6.2 → §12. Old saved `.json` downloads will not match; note that in §12.

**Add a site page or journey**
Edit `journeys.json` (or `index.html` for non-journey pages) → `python super-travel/build.py` → `python -m unittest test_site` → update §2 / §6.4 if the surface or fields changed.

**Add an API route** (Option B is built; this is how to extend it)
1. Add the route inside `create_app` in `api.py`; call `llm`/`tools`/`content`, copy no logic. Validate bodies with a pydantic model that sets length limits.
2. Rate-limit it if it costs money or writes to disk.
3. Test in `test_api.py` with `ApiTestCase.make_client` (fake session, fake clock, temp contact file).
4. Update the route table and behaviour notes in §4, §2 if the site uses it, §9, §12.

**Swap or add an LLM provider**
Implement a `ChatSession`-compatible class (`send(text, on_event) -> TurnResult`) in its own module; reuse `prompts`, `schemas`, `tools.run_tool`, `llm.ChatError`; extend `KEY_VARS`, `provider()`, `new_session()`, `.env.example`, §7; add `test_<provider>.py`.

## 11. Decisions and known drift

| Date | Decision / fact | Why |
|---|---|---|
| 2026-09 | Two model calls per turn (tools, then JSON) | Tools + strict JSON in one call is unreliable across models |
| 2026-09 | Totals recomputed in Python (`_reconcile`) | Models miscount; the budget banner must be right |
| 2026-09 | Tools return `{"error"}` instead of raising | The model can read it and react; the UI never sees a stack trace |
| 2026-09 | No database, accounts or bookings | Class demo scope (`requirements.md` §4) |
| 2026-10 | OpenRouter added beside Gemini | Gemini free-tier limits during demos |
| 2026-10 | Site generated from `journeys.json` by `build.py` | One source of truth; tests catch stale pages |
| 2026-10-05 | HTTP API built (FastAPI, in-memory sessions, file-based contact, no database) | The skeleton's open backend items; stays inside the no-database, no-accounts scope |
| 2026-10-05 | `ChatError` is HTTP 200 + `error` field, not a 4xx/5xx | The UI shows it like a reply; transport errors stay real status codes |
| 2026-10-05 | OpenRouter requests have a 90 s hard deadline in a daemon thread | `requests` timeouts reset on keep-alive bytes, so a queued free model could hang forever |
| 2026-10-05 | Plan docs (`requirements.md`, `build-plan.md`, `roadmap.md`) are out of date; this file and the code are current | Features outgrew the original plan |
